[#UC_01_09]
== UseCase_01_09: Client authentisierung und autorisierung software attest SC 403

.UseCase_01_09
[cols="1,1a",options="autowidth"]
|===
| *Titel:* | Client authentisierung und autorisierung software attest SC 403

| Akteur: |
*MA einer LEI*

| weitere Akteure: |
- *ZETA Client*
- *Konnektor / TI-Gateway*
- *SMC-B*
- *PEP HTTP Proxy*
- *PDP Authorization Server*
- *PDP Policy Engine*

| Auslöser: |
Ein MA einer LEI möchte auf einen Resource Server zugreifen und muss sich dafür authentisieren und autorisieren.

| Kurzbeschreibung: |
Um auf einen Resource Server zugreifen zu können, benötigt der
Client ein Access Token vom PDP Authorization Server.
Stationäre ZETA Clients verwenden dafür den Token Exchange Flow mittels Software-Attestierung. +

Der Token-Austausch mittels Software-Attestierung wird vom PDP Authorization Server mit ``403 Forbidden`` abgelehnt,
wenn der Request grundsätzlich verarbeitet werden kann, der Client jedoch keine Berechtigung für die angeforderte Ressource erhält.
Hier liefert die Policy Engine ``allow = false`` trotz technisch gültiger Credentials. Der AS antwortet mit ``403/access_denied``. Ungültige Grants und DPoP-Proofs gehören zu UseCase_01_07, fehlgeschlagene Client-Authentifizierung zu UseCase_01_08.
In diesem Fall stellt der PDP Authorization Server keine Tokens aus.

| Vorbedingung: |
Der stationäre ZETA Client ist bereits beim ZETA Guard registriert, d.h. es existiert bereits eine
``client_id`` inklusive zugehörigem Schlüsselpaar.
Der Client hat keine bestehende Session (kein gültiges Refresh Token).
Credentials, SMC-B-Subject-Token und Softwareattestierung sind technisch gültig.
Die kontrollierte Policy-Entscheidung liefert result.allow=false und result.reasons={"UC_01_09_policy_denied": true}. Ihr Empfang beim AS und die direkte Fehlerantwort sind derselben Transaktion zuordenbar; ein vorgelagerter Credential-/Attestierungsfehler ist damit ausgeschlossen.
Die ausführbaren Token-/Policy-Prüfungen verwenden das vollständige Laufzeit-Bundle schemas/v_2_0. Für user_info gilt unverändert schemas/v_2_0/schemas/zeta-user-info.yaml mit commonName, professionOID und organizationName. Bei widersprechenden Feldnamen oder Wertebereichen in der Spec ist das gepinnte Schema maßgeblich.

| Nebenbedingung: |
Keine zusätzlichen Nebenbedingungen.

| Ablauf: |
Die folgenden JWT-Darstellungen sind Ausschnitte des CC-Profils gemäß `schemas/v_2_0`; sie ersetzen keine vollständige Schemaprüfung. Auslassungen und Platzhalter werden vor dem Signieren typgerecht ergänzt: `exp` und `iat` sind ganzzahlige NumericDate-Werte in Sekunden, `aud` ist das dargestellte String-Array. Header, Pflichtclaims und die im jeweiligen Flow erforderlichen frischen AS-Nonces und Schlüsselbindungen müssen vollständig und gültig sein. Bei einer Negativvariante wird anschließend ausschließlich der ausdrücklich benannte Fehlergrund verändert.

. MA startet *Authentisierung/Autorisierung-Prozess (Token-Austausch)* über den ZETA Client.
. Der ZETA Client fordert beim PDP Authorization Server eine Nonce an:
- ``GET /nonce``
. Der PDP Authorization Server liefert ``200 OK`` mit einer neuen Nonce zurück.
. Der ZETA Client erstellt ein *DPoP Key Pair* (sitzungsbasiert).
- Zweck: Bindung für den späteren Token-Austausch.

. Der ZETA Client berechnet eine *attestation challenge*:
- ``attestation_challenge = HASH(pubKeyHash + nonce)``

. Der ZETA Client erstellt ein *Client Statement* mit *posture-software*.
+
.client_statement:
[source,txt]
----
- sub
- product_id
- product_version
- posture (containing attestation_challenge etc.)
- attestation-info
----
+

. Der ZETA Client erstellt ein *Client Assertion JWT*.
+
.Client Assertion JWT Claims (with Attestation):
[source,json]
----
{
"iss": "<client_id>",
"sub": "<client_id>",
"aud": ["<AS_Token_Endpoint_URL>"],
"exp": "...",
"jti": "...",
"client_statement": {}
}
(sig by Client_Instance_Private_Key)
----
+

. Der ZETA Client erstellt ein *SMC-B Subject Token* (JWT).
+
.SMC-B Subject Token Claims (Auszug):
[source,json]
----
{
"iss": "<client_id>",// Issuer is the client
"sub": "<Telematik-ID from SMC-B>",// Subject is the institution
"aud": ["<AS_Token_Endpoint_URL>"],// Audience is the Authorization Server
"exp": "...",// Short-lived
"iat": "...",
"jti": "...",
"scope": "..." // As required for the Resource Server access
}
----
+

. Der ZETA Client initiiert eine *External Authenticate*-Anfrage beim Konnektor / TI-Gateway:
- Übermittlung des JWT-Hash.
. Der KTG reicht den Hash an die SMC-B weiter.
. Die SMC-B antwortet mit signiertem Hash.
. Der KTG liefert die *JWT-Signatur* zurück an den ZETA Client.

. Der ZETA Client fügt die JWT-Signatur in das *SMC-B Subject Token* ein.
. Der ZETA Client erstellt ein *DPoP Proof JWT* für den Token-Austausch.
- Enthält Claims für den Token Request.
+
.DPoP Proof JWT Claims (for Token Exchange):
[source,json]
----
{
"typ": "dpop+jwt",
"alg": "ES256",
"jwk": { ... }
}.{
"jti": "...",
"htm": "POST","htu": "<AS_Token_Endpoint_URL>",
"nonce": "<nonce from AS>", // Binding to AS
"iat": "..."
}.(sig by DPoP_Private_Key)
----
+

. Der ZETA Client sendet einen *Token Request* (<<RFC8693, RFC 8693>>) an den PDP Authorization Server:
- Enthält ``DPoP: signed_dpop_jwt``.
+
.Token Exchange Request Body:
[source,txt]
----
grant_type=urn:ietf:params:oauth:grant-type:token-exchange
&subject_token=<SMC-B_Subject_Token>
&subject_token_type=urn:ietf:params:oauth:token-type:jwt
&client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer
&client_assertion=<Client_Assertion_JWT>...
----
+

. Der PDP Authorization Server validiert den Request:
- Client Assertion
- Attestation
- DPoP Proof
- Subject Token
. Der PDP Authorization Server ruft die Policy Engine (PDP-PE) auf:
- ``POST /v1/data/authz`` mit Input-Parametern.

. Die Policy Engine verweigert den Zugriff mit dem vorbereiteten result.allow=false und Testgrund. Die Testsuite bestätigt den Empfang genau dieser Entscheidung beim AS, bevor sie die direkte Tokenantwort auswertet.
. Der PDP Authorization Server setzt die negative Policy-Entscheidung als Fehlerantwort gemäß https://www.rfc-editor.org/rfc/rfc6749#section-5.2[RFC 6749, Abschnitt 5.2] um und stellt keine Access- oder Refresh-Token aus.
. Der PDP Authorization Server antwortet dem ZETA Client mit ``403 Forbidden`` und Fehlerdetails.
. Der direkte Antwortkörper entspricht dem Zweig denyResponse von token-response.yaml einschließlich zeta-error.yaml.
. Der Authorization Server übernimmt result.reasons derselben korrelierten Policy-Entscheidung unverändert in das reasons-Feld der Ablehnungsantwort.
. Der ZETA Client informiert den MA über den abgelehnten Zugriff.

| Nachbedingung: |
Es wurden keine Access- oder Refresh-Token ausgegeben. Der Zugriff auf den Resource Server bleibt verwehrt.
Das Fehlerobjekt entspricht dem Fehlerzweig von token-response.yaml und zeta-error.yaml; reasons stimmt mit result.reasons derselben Policy-Entscheidung überein.
