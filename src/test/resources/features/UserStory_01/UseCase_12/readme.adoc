[#UC_01_12]
== UseCase_01_12: Client-Ressourcenanfrage an den Fachdienst (SC 200)

.UseCase_01_12
[cols="1,1a",options="autowidth"]
|===
| *Titel:* | Client-Ressourcenanfrage an den Fachdienst (SC 200)

| Akteur: |
*MA einer LEI*

| weitere Akteure: |
- *Fach-Client*
- *ZETA Client*
- *PEP HTTP Proxy*
- *Resource Server*

| Auslöser: |
Ein MA einer LEI möchte über den ZETA Client eine geschützte Ressource abrufen und benutzen.

| Kurzbeschreibung: |
Der ZETA Client sendet eine Anfrage mit einem Access Token für eine geschützte Ressource an den PEP HTTP Proxy.
Dieser überprüft die Gültigkeit des Tokens und leitet die Anfrage bei erfolgreicher Prüfung an den Resource Server
weiter.
Auch ein unbekannter nicht kritischer JOSE-Header-Parameter im ansonsten gültigen DPoP Proof verhindert den Ressourcenzugriff nicht.

Der Client erhält daraufhin die angeforderte Ressource.

| Vorbedingung: |
Der stationäre ZETA Client ist bereits beim ZETA Guard registriert, d.h. es existiert eine
``client_id`` inkl. zugehörigem Schlüsselpaar.
Der ZETA Client verfügt über eine bestehende Session mit einem gültigen Access Token für den Resource Server und
zugehörigem Refresh-Token.
Der PDP Authorization Server hat beim erfolgreichen Token-Austausch ``product_id`` und ``product_version`` aus der Selbstauskunft sowie ``professionOID`` aus dem SMC-B-Zertifikat verarbeitet und protokolliert.

| Nebenbedingung: |
- Keine Bereitstellung von *PoPP-Token* für Ressourcenanfrage notwendig. <<A_26477-01>>
- Weiterleitung der *Client-Daten* an Resource Server ist deaktiviert. <<A_26492-02>>
- Der dargestellte Basisablauf erfolgt ohne Verwendung von *ZETA/ASL*. <<A_29381>> Die JOSE-Headervariante legt keinen ASL-Modus fest.
- In der WebSocket-Variante werden WebSocket-Verbindungen für die Ressourcenanfragen seitens ZETA Client und PEP HTTP Proxy verwendet. <<A_26639>> <<A_26195>>

| Ablauf: |
1. MA startet den Abruf einer geschützten Ressource über den Fach-Client.
2. Der Fach-Client ruft den ZETA Client auf:
- ``GET /resource``
3. Der ZETA Client erstellt einen an die Ziel-URL des Resource Servers gebundenen *DPoP Nachweis*.
4. Der ZETA Client ruft die Ressource am PEP HTTP Proxy auf:
- ``GET /resource``
- ``Authorization: DPoP ... (Access Token)``
- ``DPoP: ... (DPoP Token)``
5. Der PEP HTTP Proxy prüft das *Access Token*.
6. Der PEP HTTP Proxy prüft den *DPoP Nachweis*. In der JOSE-Variante enthält der Proof einen zusätzlichen unbekannten Header-Parameter ohne `crit`. Signatur, Ziel, Methode, Zeitwerte, der Access-Token-Hash `ath` und die Bindung des Proof-Schlüssels an `access_token.cnf.jkt` bleiben gültig. Der PEP ignoriert den unbekannten Parameter und setzt den erfolgreichen Ablauf fort.
7. Der PEP HTTP Proxy verarbeitet und protokolliert für den Ressourcenaufruf die Produktkennung ``product_id``, die Produktversion ``product_version`` und die Berufsgruppe ``professionOID``.
8. Der PEP HTTP Proxy erzeugt zusätzliche HTTP-Header:

* *zeta-user-info*:
** Format: ``Base64-URL kodierte JSON Struktur des User-Info Inhalts``
** Schema: link:https://raw.githubusercontent.com/gematik/zeta/refs/heads/main/src/schemas/zeta-user-info.yaml[zeta-user-info.yaml]

9. Der PEP HTTP Proxy leitet die Anfrage mit den vorgesehenen ZETA-Kontextheadern an den Resource Server weiter:
* ``GET /resource``-Anfrage
** mit vorhandenen HTTP header
** zusätzlich erstellte PEP HTTP Header als JSON
10. Der Resource Server antwortet dem PEP HTTP Proxy mit ``200 OK`` und der angeforderten Ressource.
11. Der PEP HTTP Proxy gibt die Antwort ``200 OK`` und Ressource zurück an den ZETA Client.
12. Der ZETA Client gibt die Antwort ``200 OK`` und Ressource zurück an den Fach-Client.
13. Der Fach-Client stellt die Ressource dem MA bereit.

| Nachbedingung: |
Der MA hat über den Fach-Client und den ZETA Client die geschützte Ressource erfolgreich abgerufen und kann diese nun verwenden.
Für jeden Ressourcenaufruf liegen die drei Clientdaten im PEP-Protokoll vor und sind mit den zugehörigen PDP-Protokolldaten verknüpfbar.
Die protokollierten Werte stammen vom jeweils aufrufenden Client und dessen Session.
Der Ressourcenzugriff ist auch mit dem unbekannten nicht kritischen DPoP-Header erfolgreich; PEP, Resource Server und ZETA Client antworten mit HTTP 200.
