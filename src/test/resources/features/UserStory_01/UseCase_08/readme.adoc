[#UC_01_08]
== UseCase_01_08: Client authentisierung und autorisierung software attest SC 401

.UseCase_01_08
[cols="1,1a",options="autowidth"]
|===
| *Titel:* | Client authentisierung und autorisierung software attest SC 401

| Akteur: |
*MA einer LEI*

| weitere Akteure: |
- *ZETA Client*
- *PDP Authorization Server*

| Auslöser: |
Ein MA einer LEI möchte auf einen Resource Server zugreifen und muss sich dafür authentisieren und autorisieren.

| Kurzbeschreibung: |
Um auf einen Resource Server zugreifen zu können, benötigt der
Client ein Access Token vom PDP Authorization Server.
Stationäre ZETA Clients verwenden dafür den Token Exchange Flow mittels Software-Attestierung.
Bei fehlgeschlagener Client-Authentifizierung antwortet der AS mit ``401/invalid_client``. Der vorhandene Challenge-Fall setzt ein Softwareprofil voraus, das die übertragene Attestierungs-Challenge tatsächlich zur Authentisierung validiert; das fixierte Schema kennzeichnet dieses Feld inzwischen als veraltet und verweist auf `nonce`. DPoP-Fehler gehören gemäß A_25661-01 zu HTTP 400 in UseCase_01_07.
Eine separate Client-Variante simuliert gezielt eine 401-Antwort, um die erneute Authentifizierung zu prüfen; sie belegt keine serverseitige Fehlerklassifikation.
Der ZETA Client befolgt die Anweisung zur erneuten Authentifizierung, führt den Token Exchange erneut aus und erhält anschließend gültige Access Tokens.

| Vorbedingung: |
Der stationäre ZETA Client ist beim ZETA Guard registriert und besitzt eine ``client_id`` samt Schlüsselpaar.
Es liegt kein gültiges Access Token vor.

| Nebenbedingung: |
Keine zusätzlichen Nebenbedingungen.

| Ablauf: |

*Serverseitiger Antwortvertrag bei fehlerhafter Client-Authentifizierung*

. Für die fehlgeschlagene Client-Authentifizierung löst der Testdriver im genannten Challenge-Profil nach erfolgreicher frischer SDK-Kontrolle einen weiteren Token Exchange aus. Tiger verändert ausschließlich die Attestierungs-Challenge der Client-Assertion und signiert sie mit dem registrierten Client-Schlüssel neu. Die falsche Challenge wird gegen den unabhängig berechneten Hash aus JWK-Thumbprint des registrierten Client-Schlüssels und tatsächlicher AS-Nonce gemäß `posture-software.yaml` geprüft; Subject-/DPoP-Nachweise, Schlüsselbindungen, Ziele und Zeiten müssen ansonsten gültig sein. Ohne belegte aktive Challenge-Validierung ist dieser Negativentwurf blockiert; eine ignorierte veraltete Eigenschaft beweist für sich allein keine fehlgeschlagene Client-Authentifizierung.
. Die Testsuite korreliert den veränderten Request mit der ursprünglichen AS-Antwort und prüft HTTP 401/invalid_client, das Fehlerschema und das Ausbleiben neuer Tokens. Eine vom Proxy auf 401 gesetzte Antwort zählt hierfür nicht.
. Das vorhandene Challenge-Szenario prüft Manipulationsmarker, Grant-Typ, Status, Fehlercode und Schema. Die vollständige unabhängige Fehlerisolierung, ein eigener positiver Kontrolllauf und Tokenfreiheit sind darin bislang nicht vollständig umgesetzt. Diese Abdeckungslücke wird nicht als bestandener Nachweis gewertet. Die Bereinigung von Titel und Hervorhebung ändert das bisherige Prüfziel dieses unveränderten Ausgangstests nicht und begründet keine zusätzliche Implementierung.

*Separate Client-Wiederholung bei simulierter 401-Antwort*

1. MA startet den *Authentisierung-/Autorisierungs-Prozess* im ZETA Client.
2. Der ZETA Client fordert beim PDP Authorization Server eine Nonce an (``GET /nonce``).
3. Der PDP Authorization Server antwortet mit ``200 OK`` und Nonce.
4. Der ZETA Client erstellt Client Assertion und DPoP Proof für den Token-Austausch (Software-Attestierung).
5. Der ZETA Client sendet den Token-Request an den PDP Authorization Server (``POST /token``).
6. Tiger setzt ausschließlich den Status der ersten Token-Antwort auf ``401 Unauthorized``. Diese Client-Variante prüft keinen serverseitigen Fehlervertrag.
7. Der ZETA Client fordert erneut eine Nonce an (``GET /nonce``).
8. Der PDP Authorization Server antwortet mit ``200 OK`` und Nonce.
9. Der ZETA Client erstellt Client Assertion und DPoP Proof erneut.
10. Der ZETA Client sendet den Token-Request erneut (``POST /token``).
11. Der PDP Authorization Server antwortet mit ``200 OK`` und Access bzw. Refresh Token.
12. Der ZETA Client informiert den MA über die erfolgreiche Zugriffrechtserteilung.

| Nachbedingung: |
Bei fehlgeschlagener Client-Authentifizierung stellt der AS keine Tokens aus. In der separaten Wiederholungsvariante kann der Client nach erfolgreicher erneuter Authentifizierung zugreifen.
