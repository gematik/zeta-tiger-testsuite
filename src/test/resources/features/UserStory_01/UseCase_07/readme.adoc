[#UC_01_07]
== UseCase_01_07: Client-Authentisierung und -Autorisierung mit Software-Attestierung: Token-Request-Validierung

.UseCase_01_07
[cols="1,1a",options="autowidth"]
|===
| *Titel:* | Client-Authentisierung und -Autorisierung mit Software-Attestierung: Token-Request-Validierung

| Akteur: |
*MA einer LEI*

| weitere Akteure: |
- *ZETA Client*
- *Konnektor / TI-Gateway*
- *SMC-B*
- *PDP Policy Engine*
- *PDP Authorization Server*

| Auslöser: |
Ein MA einer LEI möchte auf einen Resource Server zugreifen und muss sich dafür authentisieren und autorisieren.

| Kurzbeschreibung: |
Um auf einen Resource Server zugreifen zu können, benötigt der
Client ein Access Token vom PDP Authorization Server.
Stationäre ZETA Clients verwenden dafür den Token Exchange Flow. +

Der Token-Austausch schlägt in diesem Use Case nach gültiger Client-Authentifizierung mit HTTP 400 fehl, wenn genau ein Fehler des Token-Requests, Grants oder DPoP-Proofs vorliegt.
Fehler der Client-Authentifizierung, etwa fehlende erforderliche Claims oder ungültige Attestierungsdaten in der ``client_assertion``, gehören zu 401/invalid_client in <<UC_01_08>>.
Ungültige Subject-Token-Schlüsselbindungen werden mit 400/invalid_grant, ein ungültiger DPoP-Proof mit 400/invalid_dpop_proof abgelehnt. Diese technischen Fehler sind keine Policy-Ablehnung mit 403.
Ein Token Exchange ohne erforderliche DPoP-Nonce wird bei ansonsten gültigen Signaturen, Subject-Token-Nonce und Schlüsselbindungen mit HTTP 400 und `use_dpop_nonce` beantwortet. Die Antwort enthält eine neue Nonce im `DPoP-Nonce`-Header gemäß RFC 9449 Abschnitt 8.
Eine fehlende erforderliche erneute Client-Attestierung bei einer neuen Session ist ebenfalls ein Client-Authentifizierungsfall in <<UC_01_08>>, kein pauschaler 400-Fehler dieses UseCases.
Als positive JOSE-Variante enthält der DPoP Proof einen unbekannten Header-Parameter ohne `crit`. Bei ansonsten gültigem Request und freigebender Policy wird dieser Parameter ignoriert und der Token Exchange mit HTTP 200 und Access Token abgeschlossen. Nicht unterstützte, in `crit` aufgeführte Erweiterungen werden dagegen abgelehnt. Der zugehörige Erfolgsablauf und die positive Client-Assertion-Variante stehen in <<UC_01_06>>.

| Vorbedingung: |
Der stationäre ZETA Client ist bereits beim ZETA Guard registriert, d.h. es existiert bereits eine
``client_id`` inklusive zugehörigem Schlüsselpaar.
Der Client hat keine bestehende Session (kein gültiges Refresh Token).
Für die positive JOSE-Variante sind Client-Authentifizierung, Subject Token, Signaturen, Nonces und Schlüsselbindungen gültig; die Policy Engine erlaubt die Tokenausgabe.

| Nebenbedingung: |
Keine zusätzlichen Nebenbedingungen.

| Ablauf: |
Die folgenden JWT-Darstellungen sind verkürzte Beispiele des CC-Profils. `exp` und `iat` sind ganzzahlige NumericDate-Werte in Sekunden; `aud` ist ein String-Array. Header, Pflichtclaims, frische AS-Nonces und Schlüsselbindungen sind in der jeweiligen Variante gültig, soweit nicht ausdrücklich ein Fehlerfall beschrieben wird.

1. MA startet *Authentisierung/Autorisierung-Prozess (Token-Austausch)* über den ZETA Client.
2. Der ZETA Client fordert beim PDP Authorization Server eine Nonce an:
- ``GET /nonce``
3. Der PDP Authorization Server liefert ``200 OK`` mit einer neuen Nonce zurück.
4. Der ZETA Client erstellt ein *DPoP Key Pair* (sitzungsbasiert).
- Zweck: Bindung für den späteren Token-Austausch.

5. Der ZETA Client berechnet eine *attestation challenge*:
- ``attestation_challenge = HASH(pubKeyHash + nonce)``

6. Der ZETA Client erstellt ein *Client Statement* mit *posture-software*.
+
.client_statement:
[source,txt]
----
- sub
- product_id
- product_version
- posture (containing attestation_challenge etc.)
- attestation-info
----
+

7. Der ZETA Client erstellt ein *Client Assertion JWT*.
+
.Client Assertion JWT Claims (with Attestation):
[source,json]
----
{
"iss": "<client_id>",
"sub": "<client_id>",
"aud": ["<AS_Token_Endpoint_URL>"],
"exp": "...",
"jti": "...",
"client_statement": {}
}
(sig by Client_Instance_Private_Key)
----
+
Die ``client_assertion`` einschließlich der für den gewählten Modus erforderlichen Attestierung ist gültig und bleibt für die nachfolgenden 400-Negativvarianten unverändert.


8. Der ZETA Client erstellt ein *SMC-B Subject Token* (JWT).
+
.SMC-B Subject Token Claims:
[source,json]
----
{
"iss": "<client_id>",// Issuer is the client
"sub": "<Telematik-ID from SMC-B>",// Subject is the institution
"aud": ["<AS_Token_Endpoint_URL>"],// Audience is the Authorization Server
"exp": "...",// Short-lived
"iat": "...",
"jti": "...",
"nonce": "<nonce from AS>",
"client_key": { "jkt": "<thumbprint of client instance key>" },
"dpop_key": { "jkt": "<thumbprint of DPoP key>" }
}
----
+

9. Der ZETA Client initiiert eine *External Authenticate*-Anfrage beim Konnektor / TI-Gateway:
- Übermittlung des JWT-Hash.
10. Der KTG reicht den Hash an die SMC-B weiter.
11. Die SMC-B antwortet mit signiertem Hash.
12. Der KTG liefert die *JWT-Signatur* zurück an den ZETA Client.

13. Der ZETA Client fügt die JWT-Signatur in das *SMC-B Subject Token* ein.
14. Der ZETA Client erstellt ein *DPoP Proof JWT* für den Token-Austausch.
- Nur die im jeweiligen Negativfall benannte Request-, Grant- oder DPoP-Eigenschaft ist fehlerhaft; die Client-Authentifizierung bleibt gültig.
- In der positiven JOSE-Variante enthält der ansonsten gültige Proof einen unbekannten Header-Parameter ohne `crit`. In der kritischen Variante wird die nicht unterstützte Erweiterung zusätzlich in `crit` aufgeführt.
+
.DPoP Proof JWT Claims (for Token Exchange):
[source,json]
----
{
"typ": "dpop+jwt",
"alg": "ES256",
"jwk": { ... }
}.{
"jti": "...",
"htm": "POST","htu": "<AS_Token_Endpoint_URL>",
"nonce": "<nonce from AS>", // Binding to AS
"iat": "..."
}.(sig by DPoP_Private_Key)
----
+

15. Der ZETA Client sendet einen *Token Request* (<<RFC8693, RFC 8693>>) an den PDP Authorization Server:
- Enthält ``DPoP: signed_dpop_jwt``.
+
.Token Exchange Request Body:
[source,txt]
----
grant_type=urn:ietf:params:oauth:grant-type:token-exchange
&subject_token=<SMC-B_Subject_Token>
&subject_token_type=urn:ietf:params:oauth:token-type:jwt
&client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer
&client_assertion=<Client_Assertion_JWT>...
----
+

16. Der PDP Authorization Server validiert den Request:
- Client Assertion
- Attestation
- DPoP Proof
- Subject Token
17. Nach erfolgreicher Client-Authentifizierung antwortet der PDP Authorization Server auf den isolierten Fehler mit ``400 Bad Request`` und dem dafür spezifizierten Fehlercode. Er stellt keine Tokens bereit. Insbesondere führen eine falsche ``client_key.jkt``- oder ``dpop_key.jkt``-Bindung im korrekt signierten Subject Token bei ansonsten gültigen Nachweisen zu ``400/invalid_grant``.
18. In der positiven JOSE-Variante ignoriert der PDP Authorization Server den unbekannten nicht kritischen Header und stellt bei freigebender Policy Tokens mit HTTP 200 aus.
19. Der ZETA Client informiert den MA über den fehlgeschlagenen beziehungsweise erfolgreichen Zugriff.

*Antwortvarianten*

. Fehlt ein formaler Pflichtparameter oder sind angeforderter Scope beziehungsweise Ziel unzulässig, antwortet der PDP Authorization Server bei ansonsten gültigen Credentials mit HTTP 400 und `invalid_request`, `invalid_scope` beziehungsweise `invalid_target`. Die Fehlerantwort entspricht dem ZETA-Fehlerschema und enthält keine Tokens. Die Unzulässigkeit folgt aus der AS-Konfiguration oder einer ausdrücklichen Syntaxvorgabe der zugehörigen Spezifikation. Die Scope-Syntaxvarianten stehen in <<UC_04_09>>.
. Ungültige, abgelaufene und wiederverwendete Grants werden bei ansonsten gültigen Credentials mit HTTP 400/invalid_grant, schemakonformer Fehlerantwort und ohne Tokens abgelehnt. Dazu gehören eine falsche ``client_key.jkt``- oder ``dpop_key.jkt``-Bindung im korrekt signierten Subject Token; der Ablauf von Subject Tokens ist in <<UC_04_09>> beschrieben. Die Varianten umfassen ein unverbrauchtes abgelaufenes Refresh Token sowie ein nach erfolgreicher Rotation wiederverwendetes, zeitlich noch gültiges Refresh Token derselben weiterhin aktiven Sitzung.
. Im noncepflichtigen stationären CC-Token-Exchange führt eine fehlende DPoP-Nonce bei ansonsten gültiger Client-Authentifizierung, gültigem SMC-B-Subject-Token mit frischer AS-Nonce sowie korrekten Signaturen, Schlüsselbindungen, Ziel- und Zeitwerten zu HTTP 400 mit ``use_dpop_nonce``. Die Antwort entspricht dem ZETA-Fehlerschema, enthält genau einen nichtleeren ``DPoP-Nonce``-Header gemäß RFC 9449 Abschnitt 8 und keine Tokens; eine Policy-Anfrage findet nicht statt. RFC 9449 stellt den Einsatz der Nonce-Challenge allgemein in die Entscheidung des Servers; dieser Fall betrifft den noncepflichtigen CC-Ablauf.

. Ein mathematisch gültiger DPoP Proof mit dem Schlüssel der vorherigen Session, der nicht zum Subject Token gebunden ist, führt bei gültiger Client-Authentisierung, Nonce, Ziel und Zeit zu HTTP 400 mit `invalid_grant`. Ein Proof mit ungültiger Signatur fällt dagegen unter `invalid_dpop_proof`; diese Variante ist in <<UC_04_09>> beschrieben.
. Ein unbekannter JOSE-Header ohne `crit` verändert die Verarbeitung eines ansonsten gültigen Token Requests nicht. Eine nicht unterstützte kritische JOSE-Erweiterung im DPoP Proof führt zur Ablehnung mit HTTP 400 und schemakonformer Fehlerantwort.

| Nachbedingung: |
In den Negativvarianten erhält der stationäre ZETA Client kein Access Token für den Zugriff auf die geschützte Ressource des Resource Servers.
In der positiven JOSE-Variante erhält er trotz des unbekannten nicht kritischen Headers HTTP 200 und ein Access Token. Der vollständige Antwortvertrag entspricht dem Erfolgsablauf in <<UC_01_06>>.
Bei fehlender DPoP-Nonce erhält er HTTP 400 mit ``use_dpop_nonce`` und einer neuen Nonce im ``DPoP-Nonce``-Header, ohne ausgestellte Tokens und ohne Policy-Anfrage.
