[#UC_01_26]
== UseCase_01_26: Client ressource anfrage fachdienst SC 500

.UseCase_01_26
[cols="1,1a",options="autowidth"]
|===
| *Titel:* | Client ressource anfrage fachdienst SC 500

| Akteur: |
*MA einer LEI*

| weitere Akteure: |
- *ZETA Client*
- *PEP HTTP Proxy*
- *Resource Server*
- *Betreiber*

| Auslöser: |
Ein MA einer LEI fordert eine Ressource über den ZETA Client an.

| Kurzbeschreibung: |
Der ZETA Client sendet eine Anfrage mit einem Access Token für eine geschützte Ressource an den PEP HTTP Proxy.
Der PEP HTTP Proxy leitet die Anfrage an den Resource Server weiter, erhält jedoch eine Fehlerantwort mit ``zeta-cause: Proxy``. +
Der PEP HTTP Proxy wertet dies als Fehler des HTTP Proxy, leitet die Antwort nicht an den Client weiter
und antwortet mit ``500 Internal Server Error: Allgemeiner Serverfehler. Der Client sollte den Vorgang möglicherweise zu einem späteren Zeitpunkt wiederholen oder den Nutzer auf ein Problem auf dem Server hinweisen.``.
Der ZETA Client informiert den MA und empfiehlt,
die Anfrage nach einer angemessenen Wartezeit erneut zu versuchen oder auf ein Serverproblem hinzuweisen.

| Vorbedingung: |
Der ZETA Client ist registriert, authentisiert und autorisiert.
Der Betreiber kann externe Request-URLs im PEP HTTP Proxy statisch internen Ziel-URLs zuordnen und je Route eine erwartete logische Audience hinterlegen.
Die erwartete Audience entspricht der von der Policy Engine für die Zielressource vergebenen Audience.

| Nebenbedingung: |
Der Resource Server liefert eine Fehlerantwort mit ``zeta-cause: Proxy``.
Für die Variante zur transparenten Fehlerweitergabe enthält die beim ZETA Client eintreffende HTTP-500-Antwort keinen Header ``zeta-error-origin``.

| Ablauf: |
. Der Betreiber konfiguriert eine statische Zuordnung der externen Request-URL zur internen Ziel-URL des Resource Servers.
. Ein Ressourcenabruf über eine gültige Route liefert HTTP 200.
. MA startet den Abruf einer geschützten Ressource über den ZETA Client.
. Der ZETA Client erstellt einen *DPoP Nachweis*.
. Der ZETA Client ruft die Ressource am PEP HTTP Proxy auf:
- ``GET /resource``
- ``Authorization: DPoP ... (Access Token)``
- ``DPoP: ... (DPoP Token)``
. Der PEP HTTP Proxy prüft das *Access Token*.
. Der PEP HTTP Proxy prüft den *DPoP Nachweis*.
. Der PEP HTTP Proxy leitet die Anfrage an den Resource Server weiter.
. Der Resource Server antwortet mit einer Fehlerantwort und setzt ``zeta-cause: Proxy``.
. Der PEP HTTP Proxy verwirft die Antwort vom Resource Server und antwortet mit ``500 Internal Server Error``.
. Der ZETA Client gibt HTTP 500, Body und Content-Type der PEP-Antwort unverändert an den Fachclient weiter, ohne zeta-error-origin. Bei einer Wiederholung liefert der Resource Server erneut den Proxy-Fehler.
. Der ZETA Client weist auf einen allgemeinen Serverfehler hin und informiert den MA, dass der Vorgang möglicherweise zu einem späteren Zeitpunkt wiederholt werden sollte oder ein Problem auf dem Server vorliegt.

Als Variante ändert der Betreiber bei unveränderter externer Request-URL und Token-Audience das statische Weiterleitungsziel von einer erfolgreichen Ressource auf die Ressource mit Proxy-Fehler.
Der PEP HTTP Proxy verwendet das geänderte Ziel und antwortet mit HTTP 500 statt HTTP 200.
Eine weitere Variante beschränkt die Weiterleitung auf eine explizite Route. Ein Aufruf derselben Ressource mit zusätzlichem, nicht zugeordnetem Pfadsuffix darf trotz passender Token-Audience keinen internen Resource Server erreichen.
Wird anschließend für die wiederhergestellte Erfolgsroute eine andere erwartete Audience konfiguriert, erfolgt keine Weiterleitung des weiterhin für die ursprüngliche Audience ausgestellten Tokens.

| Nachbedingung: |
Die Ressource wurde nicht geliefert.
Der MA ist informiert und kann die Anfrage nach einer angemessenen Wartezeit erneut stellen.
Die Weiterleitung folgt der statischen URL-Zuordnung und erfolgt nur mit einer passenden logischen Audience.
